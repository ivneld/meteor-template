# 설계 배경 (통합형)

이 문서는 코드를 쓰기 전에 "왜 이 구조인가" 를 판단 근거로 쓰기 위한 것이다. 규칙이 상황에 맞지 않아 보이면 여기 원칙으로 돌아가 판단하고, 그래도 어긋나면 규칙을 우회하지 말고 playbooks/rule-exception.md 를 따른다.

## 이 템플릿이 전제하는 도메인

- 요구사항이 아직 충분하지 않고, PoC 수준으로 시작해 운영하면서 요구사항이 드러나는 서비스(B2C 앱 등).
- 모델이 자주 바뀐다. 엔티티와 애그리거트를 나누면 변경마다 엔티티, 애그리거트, 매퍼를 함께 고쳐야 해서 변경 비용이 두세 배가 된다.
- 아직 모르는 모델의 모양을 저장 모델과 분리해 미리 굳히지 않는다.

도메인 규칙이 처음부터 풍부하고 명세로 알려진 도메인(PKI, SCMS 등)이면 분리형 템플릿(templates/separated)이 맞다.

## 원칙 (우선순위 순)

1. **규칙은 도메인 모델 한 곳에.** 상태 전이·계산·검증은 애그리거트, 여러 애그리거트에 걸친 규칙은 `*Policy`. 도메인 서비스와 usecase 는 사실을 꺼내 넘기고 저장할 뿐 판단하지 않는다.
2. **트랜잭션 경계는 코드에서 보인다.** 트랜잭션을 여는 곳은 usecase 와 `*Reader`/`*Writer` 뿐. 도메인 서비스는 기본 전파, 경계 조절은 usecase 만.
3. **도메인 서비스는 애그리거트 하나를 맡는다.** `XxxReader`/`XxxWriter` 는 `XxxRepository` 만. 여러 애그리거트를 엮는 일, 외부 호출은 usecase.
4. **애그리거트가 곧 JPA 엔티티다. 대신 분리형으로 옮길 수 있는 상태를 규칙으로 지킨다.** 애그리거트는 `@Entity` 이고 `*Repository` 는 Spring Data 인터페이스다. 매핑 계층이 없는 대신 다음을 지킨다.
   - 애그리거트끼리 ID 로만 참조하고 JPA 연관관계를 걸지 않는다(R-14). 지연 로딩·cascade·N+1 이 설계에 들어오지 않고, OSIV 를 끈 상태에서 api 가 엔티티를 읽어도 안전하다.
   - setter 를 두지 않고(R-15), 생성은 정적 팩토리로만(R-20). JPA 기본 생성자는 protected.
   - 더티 체킹이 되더라도 저장은 `save()` 로 명시한다(R-16).
   - `EntityManager` 를 직접 쓰지 않고, 별도 엔티티를 만들지 않는다(R-05).
   - 매핑 편의가 도메인 모델의 모양을 정하게 두지 않는다(S-09).
5. **API 계약은 도메인 모델과 분리한다.** 엔티티를 그대로 응답하지 않는다(R-12). 분리하지 않아서 아낀 매핑 비용은 사라진 것이 아니라 이 경계로 옮겨 왔다.
6. **시작을 위한 구조다.** 계층은 domain / usecase / api 셋. 미리 쪼개지 않는다.
7. **지금도 이득을 주는 대비만 한다.** 위 4번의 규율은 지금도 이득(지연 로딩 사고 없음, 단위 테스트 가능)을 주므로 대비가 아니라 규칙이다.

## 분리형으로 옮길 신호

아래가 보이면 에이전트는 코드를 고치기 전에 사람에게 알린다. 옮기는 결정과 순서는 docs/scaling.md 에 있다.

- 지연 로딩, cascade, 더티 체킹이 설계를 좌우하기 시작한다.
- 도메인 규칙 테스트에 DB 가 필요해진다.
- 같은 애그리거트에 저장 모양이 둘 이상 필요하다.
- JPA 요구(기본 생성자, 가변 필드, 프록시) 때문에 불변식을 지키기 어렵다. S-09 위반이 반복된다.
- 도메인을 두 번째 실행 모듈이나 다른 애플리케이션과 공유해야 한다.

## 하지 않는 것

- 도메인별 패키지·모듈로 미리 쪼개기, 메시지 브로커·Outbox, 서비스 간 HTTP.
- 화면용·조회용 두 번째 엔티티. 조회는 `*Reader` 와 Spring Data 쿼리로.
- `*Service`, `*Manager` 같은 역할 없는 이름.
