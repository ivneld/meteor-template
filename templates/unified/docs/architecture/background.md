# 설계 배경과 원칙

이 장은 통합형 템플릿이 왜 이런 모양인지 설명한다. 규칙 하나하나는 뒤의 장에 있고, 규칙이 상황에 맞지 않을 때 돌아올 곳이 이 장이다.

## 이 템플릿을 고르는 상황

통합형은 애그리거트가 곧 JPA 엔티티다. 요구사항이 처음부터 충분하지 않고, PoC 수준으로 먼저 만든 뒤 운영하면서 요구사항이 분명해지는
B2C 서비스에 맞다.

- **모델이 자주 바뀐다.** 요구사항이 바뀔 때마다 엔티티, 애그리거트, 매퍼를 함께 고쳐야 하면 변경 비용이 두세 배가 된다. 엔티티 하나만
  고치면 되는 구조가 이 시기에는 더 싸다.
- **아직 모르는 모양을 굳히지 않는다.** 모델의 모양을 모르면서 저장 모델과 분리하면 잘못된 추상화가 두 겹으로 굳는다.

도메인 규칙이 처음부터 풍부하고 표준·명세로 미리 알 수 있는 도메인(PKI, SCMS, 결제·정산 코어)이라면 분리형 템플릿이 맞다. 두 템플릿의
비교는 저장소 루트의 README 에 있다.

분리하지 않는다고 매핑 비용이 사라지지는 않는다. 엔티티를 API 응답으로 그대로 내보내면 스키마와 API 계약이 묶이므로, 매핑은 엔티티와 API
사이로 자리를 옮긴다. 그래서 이 템플릿도 요청·응답 객체를 따로 둔다(R-12).

## 나중에 분리할 수 있게 지키는 규율

통합형을 고르는 것은 "지금은 분리하지 않는다"는 결정이지 "영원히 분리하지 않는다"는 결정이 아니다. 그 결정이 유효하려면 나중에 분리할 수
있는 상태를 유지해야 하고, 그 규율이 없으면 "나중에 분리"는 오지 않는다. 이 템플릿은 그 규율을 구조 규칙으로 강제한다.

| 규율 | 규칙 | 지키지 않으면 |
|---|---|---|
| 애그리거트끼리는 ID 로만 참조하고 JPA 연관관계를 걸지 않는다 | R-14 | 지연 로딩과 cascade 가 애그리거트 경계를 무너뜨린다 |
| setter 를 두지 않고 상태는 규칙을 가진 메서드로만 바꾼다 | R-15 | 규칙이 서비스로 흩어지고 엔티티가 빈약해진다 |
| 바꾼 애그리거트는 더티 체킹에 기대지 않고 save 한다 | R-16 | 분리형으로 옮기는 순간 저장이 조용히 사라진다 |
| JPA 용 기본 생성자는 protected 로 두고 정적 팩토리로만 만든다 | R-20 | 불변식을 건너뛴 객체가 생긴다 |
| `EntityManager` 를 직접 쓰지 않는다 | R-05 | 영속성 컨텍스트 동작에 기대는 코드가 퍼진다 |
| Hibernate 전용 API 와 생명주기 콜백에 규칙을 두지 않는다 | R-01, S-09 | 영속 기술이 도메인 모델 모양을 정하기 시작한다 |
| API 응답에 엔티티를 쓰지 않는다 | R-12 | 스키마와 API 계약을 따로 바꿀 수 없다 |

## 분리형으로 옮길 신호

아래 신호가 반복되면 그 애그리거트를 분리형으로 옮길 때가 된 것이다. 옮기는 순서는 [구조 확장](../scaling.md#분리형으로-옮기기).

- 지연 로딩, cascade, 더티 체킹이 설계를 좌우하기 시작한다.
- 도메인 규칙을 테스트하는 데 DB 가 필요해진다.
- 같은 애그리거트에 저장 모양이 둘 이상 필요해진다(조회용 추출 컬럼, 큰 본문의 분리 저장).
- JPA 의 요구(기본 생성자, 가변 필드, 프록시) 때문에 불변식을 지키기 어려워진다.
- 도메인 모델을 두 번째 실행 모듈이나 다른 애플리케이션과 공유해야 한다.

옮기는 단위는 애플리케이션 전체가 아니라 애그리거트다. 결제처럼 규칙이 명확하고 틀리면 비싼 애그리거트만 먼저 옮기고, 설정·공지처럼
CRUD 에 가까운 애그리거트는 그대로 둘 수 있다.

## 설계 원칙

규칙은 모두 아래 일곱 원칙에서 나온다.

### 1. 시작을 위한 구조다. 계층은 셋이다

이 템플릿은 애플리케이션의 초기 시작을 위한 것이다. 도메인마다 패키지를 나누는 버티컬 슬라이스, 컨텍스트 사이의 Facade·이벤트 통로 같은
장치는 두지 않는다. 코드는 `domain`, `usecase`, `api` 세 계층으로만 나누고, 각 계층 안에서는 도메인별 하위 패키지를 만들지 않는다.
한 패키지가 감당하기 어려울 만큼 커지면 그때 나눈다([구조 확장](../scaling.md)).

### 2. 규칙은 도메인 모델 한 곳에 모은다

"CREATED 일 때만 결제할 수 있다" 같은 규칙은 애그리거트에, 여러 애그리거트에 걸친 규칙은 `*Policy` 에 둔다. 애그리거트는 JPA 매핑
어노테이션을 갖지만 Spring 은 모르고, 어노테이션은 규칙 실행에 영향이 없어 목 없이 단위 테스트한다. 도메인 서비스와 usecase 는 사실을
꺼내 넘기고 저장할 뿐 스스로 판단하지 않는다. 규칙을 바꿀 때 고칠 곳이 하나여야 한다.

### 3. 도메인 서비스는 애그리거트 하나를 맡는다

리포지토리 호출과 공통 도메인 처리는 도메인 서비스(`*Reader`, `*Writer`)에 모은다. 도메인 서비스가 커지는 길은 대부분 다른 애그리거트의
저장소나 다른 도메인 서비스를 부르는 데서 열린다. 그래서 도메인 서비스 하나는 자기 애그리거트와 자기 `*Repository` 만 다루고, 여러
애그리거트를 엮거나 외부 시스템을 부르는 일은 전부 usecase 로 올린다. 이름은 역할이 드러나는 닫힌 어휘만 쓴다.

### 4. 트랜잭션 경계는 코드에서 보여야 한다

도메인 서비스와 usecase 모두 트랜잭션을 선언할 수 있다. 도메인 서비스는 기본 전파(`REQUIRED`)만 써서 혼자 불리면 독립된 트랜잭션이
되고, usecase 가 연 트랜잭션 안에서 불리면 거기에 참여한다. 경계를 조절하는 일(여러 도메인 서비스를 한 트랜잭션으로 묶기, 의도적으로
나누기, `REQUIRES_NEW`)은 usecase 만 한다.

### 5. 영속화 기술은 JPA 로 고정하고, 애그리거트가 곧 엔티티다

한번 DB 에 두기로 한 데이터를 다른 저장소로 옮기는 일은 드물다. 그래서 저장소를 갈아끼우기 위한 인터페이스는 두지 않는다. `*Repository`
는 Spring Data 인터페이스 그 자체다. 애그리거트가 곧 엔티티라 변환 코드가 없고, 값 객체는 `@Embeddable` record 로 애그리거트 컬럼에
펼쳐 저장한다. 대신 위의 규율로 분리형으로 옮길 수 있는 상태를 지킨다. 자세한 득실은 [영속화](persistence.md).

### 6. API 계약은 도메인 모델과 분리한다

요청·응답 객체에는 도메인 타입을 쓰지 않는다. 애그리거트가 엔티티이므로 더 중요하다. 엔티티를 그대로 응답하면 JSON 직렬화가 스키마와
API 를 묶는다([api 계층](api.md)).

### 7. 지금도 이득을 주는 대비만 한다

미래를 위한 장치는 매일 복잡도라는 이자를 낸다. 엔티티와 애그리거트를 미리 나누지 않는 것도 이 원칙에서 나온다. 분리할 수 있는 상태를
지키는 규율은 그 자체로 지금 이득(규칙의 응집, 경계가 보이는 트랜잭션)을 주므로 둔다.

## 규칙은 어떻게 강제되는가

| 수단 | 맡는 규칙 | 성격 |
|---|---|---|
| ArchUnit (`./gradlew test` 의 `ArchitectureRules`) | R-xx 구조 규칙 | 결정적. 위반이면 빌드가 실패한다 |
| 리뷰 에이전트 (`/arch-review`) | S-xx 의미 규칙 | 코드 구조만으로 판단할 수 없는 것. PR diff 와 주변 코드를 본다 |
| 사람 | 설계 판단 | usecase 가 필요한지, 트랜잭션을 나누는 게 맞는지, 분리형으로 옮길 때인지 |

가장 강한 강제 수단은 레퍼런스 코드다. 사람은 문서보다 옆 코드를 복사하므로 `member`, `order`, `payment` 세 도메인이 규칙을 어기지 않게
유지한다. 전체 규칙 목록은 [규칙 인덱스](rules.md).
