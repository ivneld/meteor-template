# 아키텍처 확장 가이드

구조는 필요가 생겼을 때 한 단계씩 키운다. 이 템플릿은 `domain`, `usecase`, `api` 세 계층으로 시작하고, 대부분의 성장은 그 안에서
해결된다. 판단의 기준은 [설계 원칙](architecture/background.md#설계-원칙), 특히 "지금도 이득을 주는 대비만 한다"이다.

## 트리거와 대응

| 트리거 | 하지 말아야 할 것 | 해야 할 것 |
|---|---|---|
| 새 기능·도메인이 생겼다 | 새 애플리케이션이나 모듈부터 만든다 | 같은 계층에 클래스를 추가한다. [새 기능 추가](architecture/changing-rules.md#새-기능-추가) |
| `domain` 패키지가 너무 커져 한눈에 들어오지 않는다 | 계층 구조를 버리고 기능별로 다시 짠다 | 계층은 유지한 채 그 안에 도메인별 하위 패키지(`domain.order`, `domain.payment`)를 만든다. 패키지 이동만으로 끝나며 ArchUnit 규칙은 `com.meteor.domain..` 패턴이라 그대로 동작한다 |
| `*Writer` 하나가 비대해졌다 | `*Service`, `*Manager` 같은 새 이름으로 쪼갠다 | 먼저 규칙이 Writer 에 새어 있지 않은지(S-04) 보고 애그리거트·Policy 로 내린다. 그래도 크면 `*Writer` 를 둘로 나누되 이름은 `*Writer` 로 끝낸다 |
| 전체 요청이 늘어 응답이 느리다 | 코드를 나눈다 | 인스턴스를 늘린다. 앱은 무상태이므로 코드 변경이 없다. 먼저 병목이 앱인지 DB인지 외부 API인지 지표로 확인한다 |
| 조회 API 가 무겁다 | 인스턴스를 늘린다 | 조회 전용 `*Reader` 메서드와 Spring Data 쿼리로 필요한 컬럼만 읽고 캐시한다. 여러 테이블을 묶는 화면은 조회 전용 `*Reader` 에서 JOIN 쿼리로 만든다 |
| 외부 API 호출이 느려 DB 커넥션이 마른다 | 커넥션 풀만 늘린다 | 그 유스케이스를 `TransactionTemplate` 으로 나눠 외부 호출을 트랜잭션 밖으로 뺀다. [트랜잭션 나누기](architecture/transactions.md#나누기) |
| 같은 저장소에 배치·어드민 같은 두 번째 실행 모듈이 필요하다 | 도메인 규칙을 새 모듈에 복사한다 | [core-domain 모듈 추출](#core-domain-모듈-추출) |
| 지연 로딩·더티 체킹이 설계를 좌우하거나, 저장 모양이 도메인 모양과 달라진다 | 애그리거트에 매핑 편의용 필드와 콜백을 덧붙인다 | 그 애그리거트를 [분리형으로 옮긴다](#분리형으로-옮기기) |
| 새 애플리케이션이 이 애플리케이션의 데이터·규칙을 필요로 한다 | 새 앱이 이 앱의 DB 를 직접 읽는다. 새 앱에 규칙을 다시 구현한다 | [다른 애플리케이션과 연동하기](#다른-애플리케이션과-연동하기) |
| 팀이 나뉘어 배포를 서로 기다린다 | 코드만 나눈다 | 서비스 분리를 검토한다. 그 전에 도메인 사이 결합을 줄인다. [서비스를 나눠야 할 때](#서비스를-나눠야-할-때) |
| 멀티테넌트 서비스다 | 나중에 넣는다 | **첫날에 결정한다.** 격리 방식(스키마/컬럼), 모든 쿼리의 테넌트 조건 강제, 테넌트 단위 감사. 컬럼 방식이면 Hibernate `@TenantId` 가 조건 누락을 구조적으로 막는다 ([영속화](architecture/persistence.md)) |

트래픽, 코드 크기, 도메인 개수는 서비스 분리의 이유가 아니다. 각각 수평 확장, 패키지 정리, 모듈 추출로 해결되며 전부 하나의 배포 단위
안에서 가능하다. 분리의 이유는 **조직(독립 배포)** 과 **데이터(저장소 격리)**, **운영 등급** 에서만 나온다.

## 확장 프로세스

1. **측정한다.** 병목이 앱 스레드인지, DB 커넥션인지, 외부 API 인지 지표로 확인한다. `support/monitoring` 이 이 단계에 쓰인다.
2. **가장 싼 수단부터 쓴다.** 인스턴스 추가 → 조회 최적화·캐시 → 트랜잭션 분리 → 실행 모듈 추가(DB 공유) → 서비스 분리(DB 분리).
   각 단계는 앞 단계로 해결되지 않는다는 근거가 있을 때만 간다.
3. **규칙은 처음부터 지킨다.** 구조를 바꾸는 비용은 그동안 규칙에 낸 예외의 개수로 결정된다. 예외는 [규칙을 지킬 수 없을 때](architecture/changing-rules.md#규칙을-지킬-수-없을-때) 의
   절차대로 동결하고 ADR 로 남긴다.
4. **다시 측정한다.** 바꾼 구조가 해결하려던 지표가 실제로 바뀌었는지 본다.

## core-domain 모듈 추출

배치처럼 같은 도메인 규칙을 쓰는 두 번째 실행 모듈이 생기면 `com.meteor.domain` 과 `com.meteor.support.error` 를 라이브러리 모듈
`core/core-domain` 으로 옮긴다. core-enum 과 storage 는 이미 모듈이다.

```
core-api   ──┐
             ├──► core-domain ──► storage/db-core (JPA, BaseEntity)
core-batch ──┘         └────────► core-enum
```

- 애그리거트가 곧 엔티티이고 `*Repository` 가 Spring Data 인터페이스이므로 엔티티와 저장소가 함께 옮겨진다. 실행 모듈마다 매핑을 다시 쓰지
  않는다. 각 실행 모듈의 JPA 설정은 `CoreJpaConfig` 가 `com.meteor` 전체를 스캔하므로 그대로 동작한다.
- 도메인 모델은 R-01 로 Spring 을 모르고, domain 은 usecase·api·client 를 모르므로 파일 이동으로 끝난다.
- usecase 는 애플리케이션마다 다르므로 옮기지 않는다. 배치는 자기 모듈에 흐름과 트랜잭션 경계(예: 청크 단위 커밋)를 둔다. 도메인 서비스는
  기본 전파라 배치의 청크 트랜잭션에 그대로 참여한다.
- `ArchitectureRules` 는 core-domain 이 아니라 각 실행 모듈의 테스트에 두고 `com.meteor` 전체를 검사한다.
- 두 실행 모듈이 같은 엔티티를 다른 모양으로 저장하고 싶어지면 그것은 [분리형으로 옮길 신호](architecture/background.md#분리형으로-옮길-신호)다.

## 분리형으로 옮기기

[분리형으로 옮길 신호](architecture/background.md#분리형으로-옮길-신호)가 반복되는 애그리거트는 분리형 템플릿
(`templates/separated`)의 구조로 옮긴다. 애플리케이션 전체가 아니라 애그리거트 하나씩 옮길 수 있다. 통합형의 규율(R-14, R-15, R-16, R-20,
R-05)을 지켜 왔다면 옮기는 일은 기계적이다.

1. **storage 모듈에 엔티티를 새로 만든다.** `storage/db-core` 에 `com.meteor.storage` 패키지를 만들고 `OrderEntity` 와
   `OrderJpaRepository` 를 둔다. 테이블과 컬럼은 지금 애그리거트의 매핑을 그대로 옮긴다. 값 객체는 펼친 컬럼, 상태는 enum 컬럼이다.
   storage 모듈이 core-enum 을 의존하게 한다.
2. **`*Repository` 를 어댑터 클래스로 바꾼다.** `OrderRepository` 인터페이스를 같은 이름의 구체 클래스로 바꾸고 `OrderJpaRepository` 를
   감싸 `save` / `findById` / 쿼리 메서드에서 엔티티 ↔ 애그리거트를 변환한다. 메서드 이름과 시그니처를 유지하면 `*Reader` / `*Writer` 는
   바꾸지 않아도 된다. R-16 으로 save 를 명시해 왔으므로 더티 체킹에 기대던 곳이 없다.
3. **애그리거트에서 JPA 를 걷어낸다.** `@Entity`, `@Embedded`, `@Column` 등 매핑 어노테이션과 `BaseEntity` 상속, `protected` 기본 생성자를
   지운다. 필드를 `final` 로 바꾸고 식별자 필드를 애그리거트에 둔다. 저장소에서 되살리는 `restore(...)` 정적 팩토리를 추가한다. 값 객체의
   `@Embeddable` 도 지운다.
4. **규칙을 분리형 것으로 바꾼다.** `ArchitectureRules`, `ArchitectureRulesSelfTest` 와 fixture, `harness/rules/`, 사람용 규칙 문서를
   분리형 템플릿의 것으로 교체한다. R-05 의 내용이 바뀌고 R-21 이 생기며 S-09 가 없어진다. 애그리거트 일부만 옮기는 동안에는 R-05 를 두 방식
   모두 허용하도록 고치고 ADR 로 남긴다([규칙을 지킬 수 없을 때](architecture/changing-rules.md#규칙을-지킬-수-없을-때)).
5. **왕복 테스트를 돌린다.** `*RepositoryIT` 가 값 객체와 상태가 저장되고 되살아나는지 확인한다. 테스트에서 쓰던 `Persisted.withId` 는
   `restore` 로 바꾼다.

## 다른 애플리케이션과 연동하기

새 애플리케이션이 이 애플리케이션의 데이터나 규칙을 필요로 할 때.

1. **DB 를 공유하지 않는다.** 새 앱이 이 앱의 테이블을 직접 읽는 순간 그 스키마는 두 앱의 계약이 되어 바꿀 수 없다. 읽기 전용이라도
   마찬가지다.
2. **규칙은 API 로 연다.** 판단은 이 앱의 애그리거트가 하고 결과만 돌려주는 내부 API 를 만든다. 새 앱에 규칙을 다시 구현하지 않는다.
   예: `MemberReader.ensureActive()` → `GET /internal/members/{id}/active`.
3. **변경 통지가 필요하면 그 경계에만 메시지를 둔다.** 새 앱이 알아야 하는 변경만 발행하고, 유실을 막는 장치(Outbox 등)도 이 시점에 이
   경계에만 둔다.

## 서비스를 나눠야 할 때

조직·데이터·운영 등급 기준이 생겨 일부 도메인을 별도 서비스로 옮겨야 한다면, 그 전에 같은 애플리케이션 안에서 결합을 줄인다.

- [ ] 옮길 도메인의 클래스를 계층마다 하위 패키지(`domain.payment`, `usecase.payment`)로 모은다.
- [ ] 옮길 도메인과 남을 도메인을 함께 엮는 usecase 를 찾는다. 이 목록이 서비스 간 호출이나 메시지로 바꿀 대상이자 비용의 추정치다.
- [ ] 그 usecase 가 한 트랜잭션으로 묶고 있다면 나눌 수 있는지, 나누면 중간 상태와 재실행을 어떻게 다룰지 정한다([트랜잭션 나누기](architecture/transactions.md#나누기)).
- [ ] 옮길 도메인의 테이블을 다른 도메인이 JOIN 하는 쿼리를 없앤다.
- [ ] 테이블을 별도 DB 로 옮기는 것까지 끝낸다. DB 를 공유한 채 멈추면 분산 모놀리스가 되어 양쪽의 단점만 남는다.

## 처음부터 하지 않는 것

과도한 대비를 막는 선이다.

- 도메인별 패키지·모듈로 미리 쪼개지 않는다. 세 계층으로 시작한다.
- 도메인 사이에 Facade, 이벤트 같은 통로를 미리 두지 않는다. 여러 도메인을 엮는 일은 usecase 가 한다.
- 메시지 브로커, Outbox, 이벤트 저장소를 두지 않는다. 다른 애플리케이션과 연동하는 경계가 생길 때 그 경계에만 둔다.
- 저장소 교체를 위한 인터페이스를 두지 않는다. 영속화는 JPA 로 고정이다.
- 엔티티와 애그리거트를 미리 나누지 않는다. 나눌 신호가 보이면 그 애그리거트만 옮긴다.
- 서비스 간 HTTP, 사가, 분산 추적 인프라를 두지 않는다.
