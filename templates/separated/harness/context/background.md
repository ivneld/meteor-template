# 설계 배경 (분리형)

이 문서는 코드를 쓰기 전에 "왜 이 구조인가" 를 판단 근거로 쓰기 위한 것이다. 규칙이 상황에 맞지 않아 보이면 여기 원칙으로 돌아가 판단하고, 그래도 어긋나면 규칙을 우회하지 말고 playbooks/rule-exception.md 를 따른다.

## 이 템플릿이 전제하는 도메인

- 도메인 규칙이 처음부터 풍부하고 표준·명세로 미리 알려져 있다(PKI, SCMS, 결제·정산 코어 같은 도메인).
- 도메인 모델의 모양과 저장 모양이 원래 다르다(불변 값, 계산된 값, 조회용으로 펼친 컬럼).
- 모델이 안정적이라 엔티티 ↔ 애그리거트 매핑 비용을 오래 회수한다.

요구사항이 운영하며 드러나는 PoC·B2C 라면 통합형 템플릿(templates/unified)이 맞다. 이 저장소 안에서 템플릿을 바꾸는 판단은 사람이 한다. 에이전트는 현재 템플릿의 규칙을 따른다.

## 원칙 (우선순위 순)

1. **규칙은 도메인 모델 한 곳에.** 상태 전이·계산·검증은 애그리거트, 여러 애그리거트에 걸친 규칙은 `*Policy`. 도메인 서비스와 usecase 는 사실을 꺼내 넘기고 저장할 뿐 판단하지 않는다. 규칙을 바꿀 때 고칠 곳이 하나여야 한다.
2. **트랜잭션 경계는 코드에서 보인다.** 트랜잭션을 여는 곳은 usecase 와 `*Reader`/`*Writer` 뿐. 도메인 서비스는 기본 전파, 경계 조절(묶기, 나누기)은 usecase 만.
3. **도메인 서비스는 애그리거트 하나를 맡는다.** `XxxReader`/`XxxWriter` 는 `XxxRepository` 만. 여러 애그리거트를 엮는 일, 외부 호출은 usecase.
4. **영속화는 JPA 로 고정하되 엔티티와 애그리거트를 분리한다.** 애그리거트는 JPA 를 모르는 순수 자바(final 필드, 정적 팩토리, record 값 객체). 엔티티는 storage 모듈에 있고 도메인을 모른다. 변환은 domain 의 `*Repository` 어댑터가 한다. 그래서 애그리거트를 트랜잭션 밖으로 그대로 돌려줄 수 있고, 별도 결과 객체가 꼭 필요하지 않다.
5. **API 계약은 도메인 모델과 분리한다.** 요청·응답 DTO 에 도메인 타입을 두지 않는다.
6. **시작을 위한 구조다.** 계층은 domain / usecase / api 셋. 버티컬 슬라이스, 컨텍스트 사이 Facade·이벤트, 저장소 교체용 인터페이스를 미리 만들지 않는다.
7. **지금도 이득을 주는 대비만 한다.** 미래를 위한 추상화는 매일 복잡도라는 이자를 낸다.

## 받아들인 비용

- 애그리거트마다 `*Entity`, `*JpaRepository`, `*Repository`(save/findById/toDomain), `restore` 가 생긴다. 변환 코드는 모양이 고정되어 비용이 예측 가능하다.
- 더티 체킹, 지연 로딩, cascade 를 쓰지 않는다. 저장은 `save()` 로 명시하고(R-16) 애그리거트는 통째로 로딩한다.
- 대신 `@Version`, `@TenantId`, Envers, 2차 캐시, 스키마 검증 같은 영속 인프라 기능은 엔티티 쪽에서 그대로 쓴다.

## 하지 않는 것

- 도메인별 패키지·모듈로 미리 쪼개기. 한 패키지가 감당하기 어려워지면 계층 안에 하위 패키지를 만든다(docs/scaling.md).
- 메시지 브로커, Outbox, 서비스 간 HTTP. 다른 애플리케이션과 연동하는 경계가 생길 때 그 경계에만 둔다.
- `*Service`, `*Manager` 같은 역할 없는 이름.
