# 플레이북: 트랜잭션 나누기

외부 API 호출 동안 DB 커넥션을 잡지 않으려는 것처럼, 한 흐름을 여러 트랜잭션으로 나눠야 할 때. 본보기는 `PaymentUseCase.pay`.

읽을 규칙: R-06, R-08, R-18, S-06, S-07.

## 단계

1. 메서드에 `@Transactional` 을 붙이지 않는다. `TransactionTemplate` 을 생성자로 주입받는다(usecase 만 쓸 수 있다, R-06).
2. 구간을 정한다. 외부 호출은 구간 밖에 둔다(R-18). 함께 커밋·롤백되어야 하는 쓰기는 같은 구간 람다 안에 넣는다.
3. **앞 구간이 의미 있는 중간 상태를 남기게 한다.** 외부 호출 전에 `REQUESTED` 같은 상태로 저장해, 외부 성공 뒤 뒤 구간이 실패해도 대사할 근거가 남게 한다.
4. **뒤 구간을 재실행해도 안전하게 한다.** 애그리거트 메서드가 상태로 거절하게 한다(`Payment.approve` 는 `REQUESTED` 에서만). 외부에는 멱등 키(`paymentKey()`)를 넘긴다.
5. 외부 실패는 구간 밖에서 잡는다. 실패 상태 기록이 도메인 서비스 하나면 그 `*Writer` 를 바로 부른다(자기 트랜잭션). 잡은 뒤 `CoreException` 으로 바꿔 던진다.
6. 실패 지점마다 테스트한다: 외부 실패 → 실패 상태, 외부 성공 뒤 뒤 구간 실패 → 앞 구간 상태 유지, 뒤 구간 롤백. 본보기 `PaymentTransactionBoundaryIT`.

## 쓰지 않는 방법

- 같은 클래스의 `@Transactional` 메서드를 `this` 로 부르기. 프록시를 거치지 않아 트랜잭션이 적용되지 않는다.
- 구간을 별도 빈으로 빼기. usecase 면 R-09, 도메인 서비스면 경계가 domain 으로 샌다.
- 바깥 트랜잭션 안에서 `REQUIRES_NEW`. 커넥션을 둘 쥐어 부하 시 풀이 고갈된다.
