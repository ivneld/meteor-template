# 설계 배경과 원칙

이 장은 분리형 템플릿이 왜 이런 모양인지 설명한다. 규칙 하나하나는 뒤의 장에 있고, 규칙이 상황에 맞지 않을 때 돌아올 곳이 이 장이다.

## 이 템플릿을 고르는 상황

분리형은 애그리거트와 JPA 엔티티를 다른 타입으로 둔다. 도메인 규칙이 처음부터 풍부하고, 그 규칙을 미리 알 수 있는 도메인에 맞다.

- **모델을 처음부터 안다.** X.509 PKI, V2X SCMS, 결제·정산 코어처럼 표준이나 명세가 도메인 규칙을 먼저 정해 둔 도메인이다. 요구사항 때문에
  모델을 갈아엎는 일이 드물어서, 순수 도메인 모델에 들인 비용을 오래 회수한다.
- **도메인과 저장의 모양이 원래 다르다.** 인증서처럼 불변이고 값 객체 중심인 모델을 DER blob, 조회용으로 뽑아낸 컬럼, 지연 로딩하는
  본문으로 저장한다. 한 클래스로 두 모양을 함께 만족시키려 하면 어느 한쪽이 휜다.
- **도메인 모델을 다른 곳과 함께 쓸 가능성이 있다.** JPA 를 모르는 모델이어야 두 번째 실행 모듈이나 공유 커널로 꺼내기 쉽다.

요구사항이 운영하면서 드러나는 B2C 서비스나 PoC 라면 통합형 템플릿이 맞다. 두 템플릿의 비교는 저장소 루트의 README 에 있다.

분리하는 비용은 변환 코드다. 애그리거트마다 `*Repository` 의 `save` / `toDomain` 과 애그리거트의 `restore` 로 고정되어 있어 예측할 수 있다.
분리하지 않는다고 이 비용이 사라지지는 않는다. 엔티티를 API 계층에 그대로 내보낼 수 없으므로 매핑이 엔티티와 API 사이로 자리를 옮길 뿐이다.

## 설계 원칙

규칙은 모두 아래 일곱 원칙에서 나온다.

### 1. 시작을 위한 구조다. 계층은 셋이다

이 템플릿은 애플리케이션의 초기 시작을 위한 것이다. 도메인마다 패키지를 나누는 버티컬 슬라이스, 컨텍스트 사이의 Facade·이벤트 통로 같은
장치는 두지 않는다. 코드는 `domain`, `usecase`, `api` 세 계층으로만 나누고, 각 계층 안에서는 도메인별 하위 패키지를 만들지 않는다.
한 패키지가 감당하기 어려울 만큼 커지면 그때 나눈다([구조 확장](../scaling.md)).

### 2. 규칙은 도메인 모델 한 곳에 모은다

"CREATED 일 때만 결제할 수 있다" 같은 규칙은 애그리거트에, 여러 애그리거트에 걸친 규칙은 `*Policy` 에 둔다. 도메인 모델은 Spring 과
JPA 를 모르는 순수 객체라서 목 없이 단위 테스트한다. 도메인 서비스와 usecase 는 사실을 꺼내 넘기고 저장할 뿐 스스로 판단하지 않는다.
규칙을 바꿀 때 고칠 곳이 하나여야 한다.

### 3. 도메인 서비스는 애그리거트 하나를 맡는다

리포지토리 호출과 공통 도메인 처리는 도메인 서비스(`*Reader`, `*Writer`)에 모은다. 도메인 서비스가 커지는 길은 대부분 다른 애그리거트의
저장소나 다른 도메인 서비스를 부르는 데서 열린다. 그래서 도메인 서비스 하나는 자기 애그리거트와 자기 `*Repository` 만 다루고, 여러
애그리거트를 엮거나 외부 시스템을 부르는 일은 전부 usecase 로 올린다. 이름은 역할이 드러나는 닫힌 어휘만 쓴다.

### 4. 트랜잭션 경계는 코드에서 보여야 한다

도메인 서비스와 usecase 모두 트랜잭션을 선언할 수 있다. 도메인 서비스는 기본 전파(`REQUIRED`)만 써서 혼자 불리면 독립된 트랜잭션이
되고, usecase 가 연 트랜잭션 안에서 불리면 거기에 참여한다. 경계를 조절하는 일(여러 도메인 서비스를 한 트랜잭션으로 묶기, 의도적으로
나누기, `REQUIRES_NEW`)은 usecase 만 한다.

### 5. 영속화 기술은 JPA 로 고정한다. 엔티티와 애그리거트는 그래도 분리한다

한번 DB 에 두기로 한 데이터를 다른 저장소로 옮기는 일은 드물다. 그래서 저장소를 갈아끼우기 위한 인터페이스는 두지 않는다. `*Repository`
는 Spring Data 를 감싼 구체 클래스 하나다.

그런데도 엔티티와 애그리거트를 분리하는 이유는 두 가지다.

- **애그리거트와 값 객체를 JPA 의 간섭 없이 쓰기 위해서.** 기본 생성자, 가변 필드, 프록시, 지연 로딩, 더티 체킹 같은 JPA 의 요구가
  도메인 모델에 스며들지 않는다. 애그리거트는 `final` 필드와 정적 팩토리, 불변 record 값 객체로 규칙에만 집중한다.
- **애그리거트를 결과로 그대로 돌려주기 위해서.** 영속성 컨텍스트에 묶인 엔티티는 트랜잭션 밖으로 내보내기 어렵지만 순수 애그리거트는
  그대로 돌려줄 수 있다. 그래서 별도 결과 객체를 반드시 만들 필요가 없다.

자세한 득실은 [영속화](persistence.md).

### 6. API 계약은 도메인 모델과 분리한다

요청·응답 객체에는 도메인 타입을 쓰지 않는다. 값 객체는 원시 타입이나 api 전용 record 로 풀고, enum 은 core-enum 의 것을 그대로 쓴다.
API 계약이 도메인 모델에 묶이면 둘 중 하나를 못 바꾼다([api 계층](api.md)).

### 7. 지금도 이득을 주는 대비만 한다

미래를 위한 장치는 매일 복잡도라는 이자를 낸다. 배치처럼 도메인을 함께 쓰는 두 번째 실행 모듈이 생기면 그때 `domain` 을 core-domain
모듈로 추출한다. 저장소 어댑터를 domain 에 두고 도메인 모델이 프레임워크를 모르게 해 둔 것은 그 추출을 파일 이동으로 끝내기 위해서이고,
그 외의 대비는 하지 않는다.

## 규칙은 어떻게 강제되는가

| 수단 | 맡는 규칙 | 성격 |
|---|---|---|
| ArchUnit (`./gradlew test` 의 `ArchitectureRules`) | R-xx 구조 규칙 | 결정적. 위반이면 빌드가 실패한다 |
| 리뷰 에이전트 (`/arch-review`) | S-xx 의미 규칙 | 코드 구조만으로 판단할 수 없는 것. PR diff 와 주변 코드를 본다 |
| 사람 | 설계 판단 | usecase 가 필요한지, 트랜잭션을 나누는 게 맞는지, 규칙 자체를 바꿔야 하는지 |

가장 강한 강제 수단은 레퍼런스 코드다. 사람은 문서보다 옆 코드를 복사하므로 `member`, `order`, `payment` 세 도메인이 규칙을 어기지 않게
유지한다. 전체 규칙 목록은 [규칙 인덱스](rules.md).
