# 아키텍처 확장 가이드

구조는 필요가 생겼을 때 한 단계씩 키운다. 대부분의 성장은 하나의 애플리케이션 안에서 해결되고, 실제로 자주 생기는 구조 변화는
기존 기능을 떼어내는 것이 아니라 **새 기능을 별도 애플리케이션으로 만들어 이 애플리케이션과 연동하는 것**이다. 이 문서는 그 두 경우를
다룬다. 판단의 기준은 [ARCHITECTURE.md 의 설계 원칙](ARCHITECTURE.md#설계-원칙), 특히 "지금도 이득을 주는 대비만 한다"이다.

## 트리거와 대응

| 트리거 | 하지 말아야 할 것 | 해야 할 것 |
|---|---|---|
| 새 기능·도메인이 생겼다 (예: 결제 추가) | 근거 없이 새 애플리케이션을 만든다 | [별도 애플리케이션 판단 기준](#새-기능을-별도-애플리케이션으로-만들-것인가)에 하나도 해당하지 않으면 같은 앱에 새 컨텍스트 패키지를 추가한다. [ARCHITECTURE.md 의 새 컨텍스트 추가](ARCHITECTURE.md#새-컨텍스트-추가) |
| 전체 요청이 늘어 응답이 느리다 | 코드를 나눈다 | 인스턴스를 늘린다. 앱은 무상태이므로 코드 변경이 없다. 먼저 병목이 앱인지 DB인지 외부 API인지 지표로 확인한다 |
| 조회 API 가 무겁다 | 인스턴스를 늘린다 | 컨텍스트별 조회용 Repository 로 read model 을 돌려주고 캐시한다. 여러 컨텍스트를 묶는 화면은 `query` 컨텍스트에서 읽기 전용으로 만든다 |
| 특정 컨텍스트 트래픽이 다른 컨텍스트까지 느리게 한다 (noisy neighbor) | 서비스를 분리한다 | 1차: 해당 엔드포인트에 요청 제한·별도 스레드풀(bulkhead). 2차: 실행 모듈만 하나 더 만들어 그 컨텍스트의 UseCase·컨트롤러만 담고 게이트웨이에서 라우팅한다. 같은 저장소, 같은 DB, 같은 도메인 코드 |
| 같은 저장소에 배치·어드민 같은 두 번째 실행 모듈이 필요하다 | 도메인 규칙을 새 모듈에 복사한다 | `domain`, `repository`, `shared`, `support.error` 패키지를 라이브러리 모듈로 추출하고 두 실행 모듈이 함께 쓴다. core-enum 과 storage 는 이미 모듈이다. R-01 이 domain 의 의존을 막아 두었으므로 파일 이동으로 끝난다 |
| 컨텍스트 경계 규칙 위반이 반복된다 | 규칙을 느슨하게 한다 | 레퍼런스 코드와 리뷰 에이전트 규칙을 먼저 점검한다. 그래도 반복되면 그 컨텍스트를 Gradle 모듈로 승격해 컴파일 단계에서 막는다 |
| 새 애플리케이션이 이 애플리케이션의 데이터·규칙을 필요로 한다 | 새 앱이 이 앱의 DB 를 직접 읽는다. 새 앱에 규칙을 다시 구현한다 | [다른 애플리케이션과 연동하기](#다른-애플리케이션과-연동하기) |
| 팀이 나뉘어 배포를 서로 기다린다 | 코드만 나눈다 | 서비스 분리. 배포 단위와 릴리스 주기를 독립시킨다. [기존 컨텍스트를 떼어낼 때](#기존-컨텍스트를-떼어낼-때) |
| DB 가 병목이라 특정 컨텍스트 데이터를 따로 둬야 한다 | 앱만 늘린다 | 서비스 분리. 컨텍스트 소유 테이블을 별도 DB 로 옮긴다. 실행 모듈 분리(DB 공유)로는 풀리지 않는다 |
| 가용성·규제 등급이 컨텍스트마다 다르다 (결제 PCI, 추천은 죽어도 됨) | 전체를 같은 등급으로 운영한다 | 서비스 분리 |
| 멀티테넌트 서비스다 | 나중에 넣는다 | **첫날에 결정한다.** 격리 방식(스키마/컬럼), 모든 쿼리의 테넌트 조건 강제, 테넌트 단위 감사. 이것은 어떤 구조 변경보다 나중에 넣기 어렵다. 컬럼 방식이면 Hibernate `@TenantId` 가 조건 누락을 구조적으로 막는다 ([ARCHITECTURE.md 영속화 결정](ARCHITECTURE.md#영속화-결정)) |

트래픽, 코드 크기, 도메인 개수는 서비스 분리의 이유가 아니다. 각각 수평 확장, 경계 규칙, 컨텍스트 패키징으로 해결되며 전부 하나의
배포 단위 안에서 가능하다. 분리의 이유는 **조직(독립 배포)** 과 **데이터(저장소 격리)**, **운영 등급** 에서만 나온다.

## 확장 프로세스

1. **측정한다.** 병목이 앱 스레드인지, DB 커넥션인지, 외부 API 인지 지표로 확인한다. `support/monitoring` 이 이 단계에 쓰인다.
   지표 없이 확장하면 돈만 쓰고 끝난다.
2. **가장 싼 수단부터 쓴다.** 인스턴스 추가 → 캐시·read model → bulkhead → 실행 모듈 분리(DB 공유) → 서비스 분리(DB 분리).
   각 단계는 앞 단계로 해결되지 않는다는 근거가 있을 때만 간다.
3. **경계는 처음부터 지킨다.** 연동이나 분리의 비용은 그 시점의 코드가 아니라 그동안 규칙에 낸 예외의 개수로 결정된다.
   예외는 [ARCHITECTURE.md](ARCHITECTURE.md) 의 절차대로 동결하고 ADR 로 남긴다.
4. **다시 측정한다.** 바꾼 구조가 해결하려던 지표가 실제로 바뀌었는지 본다.

## 새 기능을 별도 애플리케이션으로 만들 것인가

새 기능을 처음부터 별도 애플리케이션으로 만드는 것도 미래에 대한 베팅이다. 도메인을 잘 모르는 채로 떼어 두면 경계가 잘못 그어진 채
굳고, 잦은 동기 호출과 DB 공유로 이어져 분산 모놀리스가 된다. 아래 중 하나 이상에 해당할 때만 별도 애플리케이션으로 만든다.

| 기준 | 예 |
|---|---|
| 다른 팀이 맡거나 배포 주기가 다르다 | 외부 파트너 연동 팀, 주 단위가 아니라 일 단위 배포가 필요한 기능 |
| 가용성·규제 등급이 다르다 | 결제 PCI 영역, 장애가 나도 본 서비스에 영향이 없어야 하는 부가 기능 |
| 런타임 성격이 다르다 | 대용량 배치, 실시간 스트림 처리, 다른 언어·프레임워크가 맞는 기능 |
| 데이터가 독립적이고 이 앱과 강한 일관성이 필요 없다 | 이 앱의 이벤트만 받아 쌓는 통계·검색 |

하나도 해당하지 않으면 이 애플리케이션의 새 컨텍스트로 시작한다. 경계를 지켜 두었다면 나중에 기준이 생겼을 때 떼어내는 비용은
감당할 수 있다.

## 다른 애플리케이션과 연동하기

새 애플리케이션이 이 애플리케이션의 데이터나 규칙을 필요로 할 때.

1. **DB 를 공유하지 않는다.** 새 앱이 이 앱의 테이블을 직접 읽는 순간 그 스키마는 두 앱의 계약이 되어 바꿀 수 없다. 읽기 전용이라도
   마찬가지다.
2. **규칙은 `*Facade` 를 API 로 열어 제공한다.** Facade 는 이미 판단 결과만 돌려주므로(R-10) 그대로 API 스펙이 된다. 새 앱에
   규칙을 다시 구현하지 않는다. 예: `MemberFacade.ensureActive()` → `GET /internal/members/{id}/active`.
3. **변경 통지는 `*Event` 를 내보낸다.** 새 앱이 알아야 하는 이벤트만 메시지로 발행한다. 이 경계를 넘는 이벤트는 커밋 후 발행이므로
   유실을 막는 장치(Outbox 등)를 이 시점에 이 경계에만 둔다.
4. **같은 트랜잭션으로 묶여 있던 협력이 경계를 넘는다면** 비동기와 보상 처리로 바꾼다. 대상은 ARCHITECTURE.md [측정](ARCHITECTURE.md#측정)의
   "같은 트랜잭션으로 묶인 리스너" 목록에서 찾는다.

## 기존 컨텍스트를 떼어낼 때

조직·데이터·운영 등급 기준이 생겨 기존 컨텍스트를 별도 서비스로 옮겨야 할 때의 체크리스트.

- [ ] 첫 대상은 가장 독립적인 것을 고른다. 알림, 정산, 검색처럼 다른 컨텍스트가 동기적으로 기다리지 않는 것. 주문처럼 모두가 참조하는
      중심 컨텍스트는 마지막이거나 영원히 남아도 된다.
- [ ] 첫 분리는 브로커·게이트웨이·서비스 간 인증·분산 추적을 한꺼번에 세워야 해서 가장 비싸다. 두 번째부터는 그 비용이 없다.
- [ ] `com.meteor.<context>` 폴더와 그 컨텍스트 접두어의 테이블이 옮길 단위다.
- [ ] 상대 컨텍스트가 부르던 `*Facade` 는 HTTP 클라이언트 구현으로 교체한다.
- [ ] 같은 트랜잭션으로 받던 리스너는 비동기 + 보상으로, 커밋 후 리스너는 브로커 + Outbox 로 바꾼다.
- [ ] 컨텍스트 소유 테이블을 별도 DB 로 옮기는 것까지 끝낸다. DB 를 공유한 채 멈추면 분산 모놀리스가 되어 양쪽의 단점만 남는다.

## 처음부터 하지 않는 것

과도한 대비를 막는 선이다. 이 선을 넘는 순간 "대비"가 아니라 "선제 분리"가 된다.

- 메시지 브로커를 두지 않는다. 이벤트는 in-process `ApplicationEventPublisher`.
- 컨텍스트마다 트랜잭션을 강제로 나누지 않는다. 함께 바뀌어야 하는 처리는 같은 트랜잭션으로 묶는다(S-05).
- Outbox, 이벤트 저장소(Spring Modulith Event Publication Registry 등)를 두지 않는다. 같은 트랜잭션 협력에는 필요 없고, 커밋 후
  부가 처리는 실패 감지로 충분하다. 경계를 넘는 이벤트가 생길 때 그 경계에만 둔다.
- 컨텍스트별 DB·스키마를 나누지 않는다. 테이블 접두어까지만.
- 컨텍스트별 Gradle 모듈로 쪼개지 않는다. storage 모듈과 core-api 안에서 패키지 + ArchUnit 으로 충분하다. 두 번째 실행 모듈이 생기거나 위반이 반복될 때 올린다.
- 서비스 간 HTTP, 사가, 분산 추적 인프라를 두지 않는다.
